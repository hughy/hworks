# kaizen

Kaizen is the Toyota practice of continuous, incremental improvement of the process; here the process is the agent system: its tools, routing, checks, and guidance. Agents keep writing the same throwaway tools, hitting the same harness bugs, and asking the same questions. kaizen turns that history into fixes. Run it every week or two over the default 14-day window; a longer gap only makes the reports noisier.

The window is 14 days unless the user names another ("/kaizen 3d", "since 2026-10-01"). Pass it to every reporter as `--since`. The session thresholds in Triage (5 for a group, 3 for a blocker class or mistake or guidance gap, 10 for a new tool) are set for 14 days: scale each by the window's days over 14, round up, and never go below 3. A 3-day window uses 3 throughout; a 28-day window uses 10, 6, and 20. Pass the scaled group threshold as `--min-sessions`, and write the window and the thresholds used at the top of the findings file. A short window sees less, so a group below its threshold there is untriaged, not resolved. Friction and open-questions rows without a date are dated by file modification time, so on a short window check each blocker event's own date before counting it.

Findings about how the operator prompts or works with agents belong to `hansei` (`../hansei/SKILL.md`), which hands its system findings to kaizen as prompts.

It keeps no state beyond its task dir: `TASK_DIR=$(<hworks>/scripts/task-dir.sh kaizen)`, run from the hworks checkout. Each run writes `findings-<YYYY-MM-DD>.md` there. Read the previous one first and, before triage, reconcile each action not yet `effective` or dropped against git, orchestrate records, and upstream flags, then update its state (see Output). A reviewed branch or open PR has not landed. An upstream flag waiting for the user to raise it is `awaiting-user`, not a failed fix.

A finding that comes back after its fix landed means the fix did not work, and goes to a higher level (see Triage). Count a recurrence only from examples dated after the fix landed: report windows overlap, so a window can still hold pre-fix events. A finding that merely drops below the triage thresholds is `unproven`, not `effective`; mark it `effective` only when sessions that exercised the fixed path show the problem is gone. On a window shorter than 14 days, an action whose fixed path no session in the window exercised is `pending` instead: too little evidence to judge, so its state carries to the next run unchanged in meaning. A recurrence after the fix still counts on any window, and so do sessions that show the fix working.

## Privacy

Transcripts hold private content: code, ticket text, tokens, names from every repo the agent touched. The reporters print it (session paths, command samples, open-question text). Nothing from them goes into this repo: not in a commit, a skill, a test fixture, or a unit brief that a public branch will carry. Keep report output in `$TASK_DIR`. A fix written into hworks states the general rule, never the session it came from. A tool or rule specific to one employer goes to the private companion repo that `adapters/local/` names, when the user has one; without one, list it for the user instead of building it. Owner names for employer-specific harness parts live in `HWORKS_OWNER_MAP` in an `adapters/local/*.env` file, not in this repo.

## Run the reporters

```sh
python3 <hworks>/scripts/kaizen-sessions.py --since <window> --min-sessions <group threshold> --top 1000 > "$TASK_DIR/sessions-<date>.txt"
python3 <hworks>/scripts/kaizen-tokens.py --since <window> --min-sessions <group threshold> --top 40 > "$TASK_DIR/tokens-<date>.txt"
<hworks>/scripts/blockers.sh --since <window> > "$TASK_DIR/blockers-<date>.txt"
python3 <hworks>/scripts/kaizen-setup.py --since <window> > "$TASK_DIR/setup-<date>.txt"
<hworks>/scripts/task-prune.sh > "$TASK_DIR/prune-<date>.txt"
```

`task-prune.sh` is a dry run: it lists bulk (clones, dependency installs, caches, large files) in task dirs idle for 14 days. Report its reclaimable total in the findings. Never pass `--apply`: deletion cannot be undone, so list `<hworks>/scripts/task-prune.sh --apply` for the user to run.

`kaizen-sessions.py` keeps only its top 15 groups per section by default, which hides most groups above the triage threshold; `--min-sessions <group threshold> --top 1000` prints exactly the groups Triage covers. If a section prints 1000 groups, rerun with a larger `--top`. `blockers.sh` prints every class. All four take `--since YYYY-MM-DD|Nd` and `--json`, and read `adapters/local/*.env` for their sources. A missing source is reported in the output, not fatal; say in the findings file which sources were missing.

- `kaizen-sessions.py` prints four sections ranked by distinct sessions: command shapes, agent-written scripts (with a `where:` split of inline, scratch, and worktree), repeated helpers, and failed-then-retried calls. Each group has `sess`, `calls`, a sample, and example session paths relative to the pi sessions dir. `[exists: <name>]` means the shape names a script or skill in hworks or in `HWORKS_TOOL_DIRS`. Set `HWORKS_TOOL_DIRS` to the companion repo's tool dirs, or it will not flag tools that live there.
- `kaizen-tokens.py` prints totals (tokens and cost by kind, model, and main session against each subagent), the share of cost on turns whose prompt exceeds `--long-context` tokens (default 150000) with the sessions that spent most that way, the baseline prompt split into parts (system-prompt sections, instruction files, listed skills, advertised agents, agent prompts, tool schemas) ranked by token-turns, tool results by shape ranked by carried token-turns, cache rewrites by cause, and an `upstream` list. Every baseline row and tool-result row names an owner: `hworks`, `local` (the operator's files outside hworks, such as the companion repo or a project's `AGENTS.md`), or `upstream:<name>`. Token-turns are a part's size times the turns that carried it, which is what it costs in cache reads. Set `HWORKS_OWNER_MAP` to name the harness's own sections and tools, or they show as `upstream:unattributed`. It also rebuilds review-loop runs from workflow notifications and child sessions: spend by loop shape (reviewers and rounds), per round with the blocking findings each round found, the second reviewer's unique blockers, and each subagent role by model and thinking level with its outcomes (reviews that blocked, coders whose first review was clean).
- `kaizen-setup.py` audits what pi loads, not what sessions did: every skill in the roots pi loads (with description length and whether `~/.agents/.skill-lock.json` manages it) and names loaded from more than one root; `settings.json` paths that are missing or pin a versioned install directory, and `agentOverrides` keys that name no agent; `~/.pi/agent/extensions` entries and broken links; leftover `*.bak`, `*.pre-*`, `*.orig`, `*~` files; guidance references (`scripts/...`, `skills/<name>`, `agents/<name>.md`, `../<name>/SKILL.md`, `/skill:<name>`) that resolve to nothing; and, for each hworks skill, agent, and extension, the harness tools, skills, and agents from recent session baselines that share its words, with an overlap score. Pass `--cwd <project>` to add a project's `.pi/` and `.agents/` dirs. Every row names an owner.
- `blockers.sh` prints classes as `source / kind / rule` with a count, distinct sessions, and the three latest events, then deferred decisions per repo and branch. Sources are guard blocks (`autonomy`), open questions (`open-questions`, by category), friction (`friction`, by who caught it, then category), subagent runs (`subagents`, `run-history`), and the harness audit log when configured.

## Accuracy contract

Both reporters are heuristics. A group is a lead, not a fact. Before acting on one, open two or three of its example sessions and confirm that the calls share a purpose, and what that purpose is. The same shape can cover unrelated work (a generic `import json` script group is mostly one-off parsing), and one purpose can be split across shapes. Counts are approximate: compare them to each other, not to a target. A script's location class comes from the path as written, so it can be wrong for a relative path written after a `cd`. Subagent sessions count separately, so one orchestrated program can inflate a group; check that its sessions span more than one parent session or repo.

`blockers.sh` has its own limits. Its `sess` column counts distinct session ids, or task paths when a row has no session; friction and open-questions rows have only a task path. Friction classes group by who caught it and category, not by shared cause, so one class can hold unrelated defects. Open-questions rows, and friction rows without a date, are dated by file modification time. Event detail is truncated: 200 characters stored, 90 printed. Before routing a blocker class, read the original `friction.md` and `open-questions.md` entries or status files and confirm one shared failure across independent runs.

`kaizen-tokens.py` estimates prompt-part sizes from characters, converted at the median chars-per-token of first turns; use the sizes to rank, not as exact counts. Owners come from paths, extension source, and `HWORKS_OWNER_MAP`; check an owner before routing on it. Baseline medians mix main sessions and subagents. A cache rewrite counts when a turn's cache read falls below half the previous turn's context; `unexplained` means no recorded event (compaction, model or thinking change, context edit, system prompt change) or idle gap explains it, which points at the harness or provider but is not proof. A large tool-result group says agents read a lot that way, not that the tool is at fault: open its examples before deciding whether the fix is guidance, a tool option, or upstream. The loop sections cover only children linked to a workflow key (the header prints how many) and only review-loop's `code-1`, `fix-N`, and `review-N-M` keys. A blocking finding is a reviewer's claim, not a verified defect, so a reviewer that blocks more is not better by that count alone; read a sample of its findings before judging it.

`kaizen-setup.py` reads files, not behaviour. An overlap score is shared words, a lead to open both parts and compare, never proof that one replaces the other. A stale-reference hit can be an intentional example or a gitignored path (`adapters/local/`) that exists only in the main checkout. "may be a builtin" means the override's agent was not found but builtins are on, so it may be fine. The overlap section sees only harness parts that appeared in session baselines in the window. Skill description lengths are exact only with PyYAML installed; without it the sources section says descriptions were parsed approximately. A skill whose frontmatter fails to parse is skipped with a note, as pi skips it. Agent frontmatter is read the way pi-subagents reads it (line-based `key: value`, not YAML), and an agent without a name or description is skipped with a note.

## Triage

Triage every group in at least 5 sessions, every blocker class in at least 3 (thresholds here are for 14 days; see the window rule above), every token row above the cut (`--top 40`), and every setup row; expect over a hundred groups in a 14-day window, most of them quick drops. Each lands in exactly one outcome. When a finding seems to fit two: an ignored tool (2) beats a new tool (1); a cause in a dependency (4) beats a check in this repo (3), which would only work around it; and a mistake a check can catch (3) beats a guidance edit (5).

Order verified findings by observed impact as well as distinct-session recurrence. Read the raw `cost` field of the related `friction.md` entries (review rounds, reverted commits, reruns) and cite it; do not combine unlike units into a score, and record a missing cost as unknown, not zero. A verified finding with high impact may be triaged below the frequency thresholds, with its impact evidence cited in its line.

Token rows route by owner. An `hworks` baseline part is outcome 5 (trim it, or move always-on text into a skill or reference loaded on demand) or a step down the outcome 2 ladder (a rule in `global/AGENTS.md` that only some tasks need). A `local` part is the same fix in the companion repo or the project it names, listed for the user when outside both. An `upstream:<name>` part, an `unexplained` cache-rewrite row, or any token cost whose cause is in the harness or a dependency is outcome 4. A tool-result group that agents read wastefully (whole files, unbounded logs) is outcome 2 when a narrower tool or option exists, outcome 5 when guidance should say how to read it, and outcome 4 only when the tool itself returns more than asked. Cite token-turns or dollars from the report as the finding's impact, and compare the next run's number for the same row to judge `effective`.

The long-context row (cost on turns over the threshold, top sessions) is mostly an operator habit, letting one session run long instead of starting fresh, which belongs to hansei. kaizen acts only on the parts hworks owns: compaction guidance, and skills or workflows that keep sessions running long (outcome 5, or 2 when a tool exists). Cite the long-context share as the impact and compare it next run.

Setup rows each land in one verdict: `remove`, `replace` (name the residue worth keeping and where it goes), `keep` (one line why), or `fix`. An hworks or local file edit routes as outcome 5 or 2, an upstream cause as outcome 4, and a setting outside the repo (pi `settings.json`, a leftover file, an installed skill) is listed for the user. A lock-managed skill cannot be edited in place: the fix names its uninstall or a local wrapper skill. Config symlinked from a dotfiles repo is good practice, never a finding.

Spend that buys quality is a tradeoff, not waste: a role's model or thinking level, the second reviewer, a later review round, the effort hughy-router picks, or running a loop at all. Never cut one on cost alone, since a missed defect usually costs more than the tokens. A lead is spend that rarely changes the result, such as a second reviewer that is almost never the only one to block, or a round that seldom finds a `prior` or `regression` blocker. It also needs the outcome side checked: `friction.md` entries caught by `reviewer`, `ci`, or the operator after a loop called the change clean, and loops that ended `unresolved`. Triage it as `investigate`: the question is whether the cheaper setting misses defects, and the evidence step is one window on the cheaper setting through a `models.d/*.conf` profile, a per-run `maxRounds` or effort, or an agent's `thinking`. The next run compares spend and missed defects on the same rows. If the cheaper setting held, the fix is an edit to `models.conf`, the effort defaults in `skills/hughy-router/SKILL.md`, review-loop's `maxRounds` default, or `agents/*.md`, as an outcome 5 brief. If it missed defects, drop the lead with that evidence.

1. Reusable tool worth building. Evidence: verified samples share one purpose; it recurs across at least 10 sessions in more than one repo or parent session; no existing tool covers it (search hworks `scripts/` and `skills/`, the companion repo, pstack, and the harness's own tools). Next step: an orchestrate unit (below).
2. Existing tool agents ignore. Evidence: a tool that covers the purpose exists (the `[exists]` flag, or one you found while checking outcome 1), and agents rebuild it by hand. Fix the routing, not the tool: the adapter (`adapters/pi.md` or the companion's), the skill's `description`, the `hughy-router` skill (`skills/hughy-router/SKILL.md`), or the prompt that told agents to do it by hand. Do not build a second tool. A tool used as intended (a gate script run on every change) is not a finding; drop it. When the fix is where the tool lives, take the first step of this ladder that the tool has not reached yet, and climb one step per kaizen run only while it keeps coming back:
   1. Its own skill. A script inside a skill about something else is found only through that skill's description; move it into a skill whose description names its own trigger. A script that serves one workflow stays in that skill.
   2. A line in `global/AGENTS.md`, only when an always-on rule needs the tool (as with `task-dir.sh`). That file loads in every session on every harness, so a line there costs tokens everywhere.
   3. A pi extension tool, whose schema sits in every prompt. The strongest and most expensive step, and pi-only.
3. Repeated agent mistake. Evidence: the same wrong action in at least 3 sessions, such as a guard block, a malformed artifact, or a retry after the same error. Hand the class and its evidence to `/skill:correct`, which picks the enforcement level.
4. Harness or dependency cause. Evidence: the cause is in pi, pi-subagents, the harness that wraps pi, an MCP server, or another dependency, shown by the run's own error text, status file, or a `kaizen-tokens.py` owner, and no change in this repo removes it. Flag it; do not draft or file anything. The findings line names the owner, what to raise, the evidence (counts, token-turns, cost), and whether an upstream issue or fix already exists when that is checkable locally, written from scratch with no transcript content. The next actor is "user", who decides whether and where to raise it. If hworks can work around it meanwhile, note the workaround as a separate finding.
5. Guidance gap. Evidence: agents made a reasonable choice the user would not want, or asked a question the guidance could have answered, in at least 3 sessions. Fix with an edit to `global/AGENTS.md` or an `agents/*.md` prompt. A guidance edit nothing enforces is the weakest fix; if the gap is a mistake a check could catch, it is outcome 3.

A finding that fits none is dropped with a one-line reason: a generic idiom with no shared purpose, a tool used as intended, a deferred decision the Autonomy rule settled correctly, or noise from a single program. Dropping is a valid outcome; forcing a weak finding into a fix costs more than missing it for one cycle.

Verified recurring harm whose cause or route is still unclear gets `investigate` instead: one discriminating question, one bounded evidence step, and the next actor. The next run resolves it into an outcome or drops it with a reason. It is not a sixth fix route, and generic idioms or single-program noise are still dropped.

After picking the outcome, add a companion Detect or Mitigate action only when the primary fix leaves a concrete gap: a way to catch the failure sooner, ideally in-session, or to make a repeat cheaper. Check what the primary route already supplies first: `/skill:correct` adds lint, CI, and test checks, and outcome 4 already allows a separate workaround finding. Route the companion as its own finding through outcomes 1-5, linked to the primary finding's id. It is never mandatory.

## Output

`$TASK_DIR/findings-<date>.md`, one line per finding:

`- [<outcome 1-5, investigate, or drop>] <id> <group or class> | <evidence: sessions, samples checked, existing tool, cost> | <next actor> | <deliverable and its completion check> | <artifact> | <state>`

The id is stable: reuse it in every run while the finding stays open, and give a companion the primary's id as its link. The next actor is an agent role, a skill such as `/skill:correct`, or "user". The artifact points at the branch, commit, or `units.json` entry, or is `upstream:<owner>` for a flag. The state is one of `open`, `awaiting-user`, `implemented` (landed, effect not yet seen), `effective`, `unproven`, or `pending` (window too short to judge). A drop keeps only its group and one-line reason, with no id. For `investigate`, the deliverable is the question and evidence step.

Then act on each outcome:

- Outcome 1: write the units for `../orchestrate/SKILL.md` (its Start step owns the format) in `$TASK_DIR/units.json`. A reporter or classifier unit needs the accuracy contract orchestrate describes.
- Outcomes 2 and 5: each edit is one brief for `../review-loop/SKILL.md`, or one orchestrate unit when there are several.
- Outcome 3: run `/skill:correct` with the classes.
- Outcome 4: the flags, grouped by owner and listed for the user. Nothing is drafted or filed.

Building runs at standard effort. Use exhaustive only for a tool whose failure is silent and costly, such as a guard, a reporter whose drop would hide a finding, or anything that deletes or rewrites. The user's questions go last in the reply, per `global/AGENTS.md`.
