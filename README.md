# hworks

A personal layer over the [pstack](./pstack/) mirror. `pstack/` is a git subtree of the mirror; edits to it go to the mirror. Everything hworks owns lives outside it.

- `global/AGENTS.md` is the global agent guidance: prose, comments, commits, PRs, autonomy, and scratch rules. `scripts/install.sh` links it to `~/.pi/agent/AGENTS.md`, `~/.claude/CLAUDE.md`, and `~/.codex/AGENTS.md`, so editing any of them edits this file.
- `scripts/install.sh [--profile <name>] [--check]` sets up a machine: the global guidance links, the agent roles and the `autonomy.ts`, `hughy-mode.ts`, and `runner-exit-guard.ts` extensions in `~/.pi/agent`, the `skills` entry in pi settings, and the scratch root. It is safe to rerun, and `--check` reports drift without changing anything.
- `skills/hughy-router/` is the entry point. Six routes, each starting from a goal, effort, and verify brief, with pstack playbooks read by path as references and the hworks deltas applied.
- `skills/review-loop/` and `workflows/review-loop.js` run a `coder` change and its review to a verdict as one pi-subagents workflow; `scripts/review-loop-args.sh` builds its args from the effort level. `node --test workflows/*.test.js` checks the loop logic.
- `scripts/review-range.py record|base|args` keeps a per-branch ledger of reviewed ranges and hashes of their exact diffs in `$TASK_DIR/reviewed.tsv`, so a review covers only commits no earlier review covered. `args` prints review-fanout args for the unreviewed range with interrogate's rubric and the effort's reviewers, and exits 3 when there is nothing to review (quick effort, or HEAD already reviewed). A rebase keeps coverage only when it replays a byte-identical diff, as after `gh stack rebase` onto a squash-merged parent. `review-loop-args.sh` starts review-loop at the covered point when the task dir holds a ledger.
- `skills/review-fanout/` and `workflows/review-fanout.js` run a review-only pass over one or more targets (a PR worktree, a plan file, a directory) as one workflow: every reviewer reads every target, a few targets at a time, and the result holds each reviewer's structured findings plus one merged list per target. Use it instead of a hand-written review script; review-loop covers a change and its review.
- `scripts/orchestrate.py` is the bookkeeping for the `orchestrate` skill: it imports work units, picks launchable ones by priority, dependencies, claims, and path overlap, prepares one branch worktree and review-loop args per attempt, records workflow results as acceptance receipts, and reconciles live units after a restart. It never launches agents or pushes. `python3 -m unittest discover -s scripts -p 'test_*.py'` runs its tests.
- `scripts/check.sh` is the hworks full check and the gate to give orchestrate and review-loop: every `scripts/test_*.py` module, `node --test workflows/*.test.js`, and each `extensions/*.test.mts`, each part its own process, up to `CHECK_JOBS` at once (default: the CPU count). It prints each part's time and the output of every failed part, and exits nonzero if any part fails. Wall time is close to the slowest module rather than the sum.
- `scripts/mutate.py [--json] SPEC` proves a test catches a bug: it applies each mutant (a text swap, or a file from a git rev such as the pre-fix source), runs the test command, and expects it to fail. A mutant of only `.go` files runs through `GOFLAGS=-overlay` and never writes the worktree; others are written in place and restored, also on SIGINT and SIGTERM. The coder and reviewer prompts use it for the fix-reverted check.
- `skills/edit-prose/` drafts and edits prose: a style guide that defers to the `global/AGENTS.md` prose rules, plus guides for design docs, issues, and PR descriptions.
- `skills/demo-video/` records a narrated demo video of a running web app: Playwright screen capture with an injected annotation layer, local Kokoro TTS for one or two voices, and ffmpeg composition timed by a clock strip drawn into every frame. `scripts/shot.mjs` screenshots pages at several viewports and reports overflow, without a video. `skills/demo-video/tests/smoke.sh` runs the chain end to end; `tests/shot.sh` checks `shot.mjs`.
- `skills/<name>` symlinks are the allowlist of pstack skills and principles that load. Some serve hughy-router routes. Others (`bro`, `teach`, `swarm`, `correct`, and the verification-skill pair) are commands to invoke directly, useful or not depending on the harness. `scripts/skill.sh enable|disable|list <name>` manages them.
- `agents/` sets the prompt and tool scope per role for pi-subagents: `coder`, `reviewer`, `explorer`, `synthesizer`.
- `extensions/autonomy.ts` is a pi extension that blocks `ask_user_question` and git commands that destroy history or uncommitted work, returning a redirect to the model. It enforces the Autonomy section of `global/AGENTS.md`. `/autonomy off` relaxes it for one session; `PI_AUTONOMY=0` disables it. `node --experimental-strip-types extensions/autonomy.test.mts` checks the classifier and the log.
- `scripts/task-dir.sh <task-slug>` prints and creates `$TASK_DIR`, the scratch directory for a task: `<root>/<host>--<owner>--<repo>/<branch>/<task-slug>`, or `<root>/_misc/<task-slug>` outside a repo. `<root>` is `${HWORKS_TASKS_DIR:-${XDG_STATE_HOME:-$HOME/.local/state}/agent-tasks}`: `$HWORKS_TASKS_DIR`, else `agent-tasks` under `$XDG_STATE_HOME` (default `~/.local/state`). `<branch>` is the branch lowercased with `/` as `--`; when that encoding can lose information (uppercase, other characters outside `[a-z0-9._/-]`, `--`, a leading `.` or `-`, or `-/` or `/-`), it gets `+` plus the first 8 hex chars of the SHA-1 of the raw name. Since the encoding never emits `+`, two different branches never share a dir, up to hash collisions. A newly created task dir gets a `.task` file recording `created`, `repo`, `branch`, `slug`, and `cwd`. `global/AGENTS.md` owns the rule to keep scratch out of repos; this script owns the layout, and every `$TASK_DIR` in hworks means its output.
- `extensions/hughy-mode.ts` is a pi extension that keeps the `hughy-router` skill in force for a session. `/hughy-mode on|off|status` sets it (no argument toggles). While on, each turn's system prompt carries a short section that points the model at `skills/hughy-router/SKILL.md`. The setting is stored in the session, so resume and fork keep it; `PI_HUGHY_MODE=1` starts new sessions with it on. Toggling changes the prompt once, which can cost a cache refill. `node --experimental-strip-types extensions/hughy-mode.test.mts` checks it.
- `extensions/runner-exit-guard.ts` is a pi extension that keeps other extensions from killing a pi-subagents async runner. The runner hosts background children in-process and ends each with a print-mode `session_shutdown` quit; an extension that answers that with `process.exit()` kills the runner before it runs gates or writes the result, and the run fails with "exited with code 0 before writing a result". Only inside a runner process, it ignores `process.exit()` calls that pass no exit code and logs each one to `~/.pi/agent/runner-exit-guard.log`. The runner's own exits pass a code. `PI_RUNNER_EXIT_GUARD=0` disables it. `node --experimental-strip-types extensions/runner-exit-guard.test.mts` checks it.
- `scripts/blockers.sh [--since 7d] [--json]` reports where runs blocked: guard blocks and asks logged by `autonomy.ts`, subagent `contact_supervisor` decision requests, idle, failed, or paused subagents, categorized `open-questions.md` entries, `friction.md` entries (work the operator, a reviewer, a test, or CI sent back, grouped by who caught it and category), and an optional harness audit log. `--cwd-match <text>` scopes it to one repo's task dirs and worktrees. Feed the output to `/skill:correct` to fix recurring classes.
- `scripts/task-prune.sh [--older-than 14d] [--apply] [--json]` reclaims space in the task root. In task dirs idle past the cutoff, it lists `.git`, `node_modules`, cache, and virtualenv dirs (whole, including files inside them, but never one under `orchestrate/` or holding a `.task` file) and other files over 1 MiB except `.md`, `.jsonl`, and `.task`. It never follows symlinks. It is a dry run unless `--apply` is passed.
- `skills/kaizen/` is continuous improvement of the agent system, run every week or two. It runs `scripts/kaizen-sessions.py`, `scripts/kaizen-tokens.py`, and `scripts/blockers.sh` over a window, verifies each finding in a few example sessions, and sends it to one fix: a new tool built through orchestrate, a routing fix for a tool agents ignore, `/skill:correct` for a repeated mistake, an upstream flag (never a draft) for a cause in the harness or a dependency, or a guidance edit. It tracks each action until later sessions show it worked. Report output stays in `$TASK_DIR`, since transcripts hold private content.
- `scripts/kaizen-sessions.py [--since 14d] [--min-sessions N] [--top N] [--cwd-match <text>] [--json]` reports, from pi session transcripts and ranked by distinct sessions, the tooling agents keep rewriting: repeated command shapes, agent-written scripts, repeated helper definitions, and calls that failed and were retried. A group that names an existing script or skill is flagged, so an ignored tool stands apart from a missing one. It uses no per-pattern rules, so its groups are leads to verify, not facts. `--cwd-match` keeps only sessions whose working directory contains the text, for a report on one project.
- `scripts/kaizen-tokens.py [--since 14d] [--min-sessions N] [--top N] [--cwd-match <text>] [--json]` reports where pi sessions spend tokens: totals by kind, model, and subagent; the always-on prompt split into sections, instruction files, skills, agents, and tool schemas, ranked by token-turns; tool results ranked by how long they stay in context; cache rewrites by cause; and, for review-loop runs, spend by loop shape, per round, for the second reviewer, and per role by model and thinking level next to each one's outcomes. Each row names an owner (`hworks`, `local`, or `upstream:<name>`), and upstream rows are listed as flags to raise, not drafted. Prompt-part sizes are estimates calibrated on first-turn token counts.
- `scripts/session-messages.py [--since 14d] [--cwd-match <text>] [--json]` prints the operator's own messages from top-level pi sessions, one session at a time, skipping subagent transcripts. A retrospective reads them to find where the operator corrected or redirected agents, which tool logs cannot show. Its output quotes transcripts, so keep it out of public repos.
- `skills/hansei/` is the operator-facing counterpart to kaizen, run every week or two alongside it. It runs `scripts/operator-signals.py` over the operator's own prompts, verifies each finding in a few example sessions, and renders a local HTML page of candid findings, each owned by `you`, `system`, or `both`, with copy-paste prompts that queue the fix. System findings go to kaizen as prompts. The page quotes the operator's prompts, so it stays in `$TASK_DIR`.
- `scripts/operator-signals.py [--since 14d] [--cwd-match TEXT]... [--min-sessions N] [--examples N] [--max-chars N] [--context] [--json]` reports, from the operator's messages in sessions they started (subagent transcripts skipped, harness injections stripped), approvals right after the agent asked permission, status checks, corrections, messages right after an interrupted turn, near-duplicate prompts across sessions, skill invocations, and how the length of a session's first prompt tracks corrections and approvals. Its signals are heuristics: leads to verify, not facts.
- `scripts/hansei-page.py <findings.json> [-o page.html]` renders hansei findings into one self-contained HTML page with a Copy button on each prompt. Its docstring holds the findings schema.
- `adapters/pi.md` maps Cursor-specific terms in pstack skills to pi.
- `models.conf` and `scripts/models.sh` hold the model roster. A profile names a model for each agent role and sets two slots that hughy-router reads for per-call overrides: `review2` (the second reviewer) and `exhaustive` (the `coder` model at exhaustive effort). `models.sh <profile>` writes the role models to pi settings as `subagents.agentOverrides.<role>.model` and leaves the agent files untouched; `models.sh show` prints the active profile. Profiles: `inherit` (session model, the default) and `anthropic`.
- `DIVERGENCE.md` records every skill not linked, with the reason and the pstack mirror commit.
- `CUSTOMIZING.md` covers forking hworks into your own layer, adding agent roles and model profiles, and writing an overlay repo.

## Rationale

hworks starts from the harness as it ships: a frontier model, its tools and subagents, `global/AGENTS.md` (installed as `~/.pi/agent/AGENTS.md`), and a brief that states the goal, the effort, and how to verify. Additions stay small and earn their place by changing what a run does. When a model handles something well from a plain brief, hworks leaves it alone.

- pstack is a reference library. A pstack skill loads when it adds behavior a plain brief does not get, or when it is useful on its own as a command. `DIVERGENCE.md` records every exclusion. Playbooks are read by path when a run stalls, the change is high-stakes, or it runs unattended. They are not scripts.
- `global/AGENTS.md` owns prose, comments, commits, PR, autonomy, and scratch rules, and applies in every session, with or without hworks skills loaded. Skills and agents point at it and do not restate it. hworks is public, so employer-specific guidance goes in an overlay repo, not in this file.
- Multi-day work with several concurrent writers belongs to a multi-agent coordinator. When the harness has one, hworks uses it and does not rebuild it. pi ships subagents, workflows, and missions but no coordinator, so `skills/orchestrate` adapts pstack's orchestrate playbook and adds only what is missing, as a script over the runtime: durable per-unit state, launch refusals (window, path overlap, worktree ownership), a freshness check on results, and restart recovery that waits out live writers rather than replaying them. It is experimental and opt-in, also for a small set of independent items. Otherwise, and below that scale, a plain brief with review-loop, `progress.md`, and git are the record.
- Model names live in `models.conf` and pi settings. Skills name roles and slots, so a new model or a provider outage is one profile switch.

## Why a layer

pstack's skills reference each other by name (`/poteto-mode` appears 120 times across `skills/`, `agents/`, and `docs/`), and eight skills call Cursor's `Task` tool. Editing those files in place risks a merge conflict at every upstream sync. A separate directory of symlinks costs nothing at sync time. The mirror stays a byte-exact input, and this repo holds every opinion.

## Install (pi)

On a new machine, install [pi](https://github.com/earendil-works/pi) with [pi-subagents](https://github.com/nicobailon/pi-subagents), plus `git`, `node`, and `python3`, then:

```bash
git clone https://github.com/hughy/hworks ~/dev/hworks
~/dev/hworks/scripts/install.sh --profile inherit
```

`global/AGENTS.md` refers to `~/dev/hworks`, so clone there or link that path to your clone. `install.sh` refuses to replace a real file that differs from what it would link, such as an existing `~/.claude/CLAUDE.md`; compare the two, move yours aside, and rerun. It removes a `global/AGENTS.md` that links to `global/AGENTS.md`, because pi reads `AGENTS.md` from every ancestor of the working directory as well as its agent dir, and would load the guidance twice under `~`. Install an overlay repo after hworks if you use one (see [Local overlays](#local-overlays)).

Then `/reload` and start a task with `/skill:hughy-router <task>`. The skills root follows symlinks, and `skillPath: ../skills` in each agent file resolves the same links.

pi-subagents resolves one model per launch and fails when it is unavailable. When a provider is down, apply another profile, for example `scripts/models.sh inherit`, then `/reload`.

Claude Code and Codex load only `skills/` through the plugin manifests. The agent files are pi-specific, so on those harnesses `hughy-router`'s roles map to the harness's own subagent and `adapters/pi.md` does not apply. Symlink following on those harnesses is unverified.

## Local overlays

Two gitignored paths hold machine- or employer-specific setup without changing tracked files:

- `models.d/*.conf`: extra profiles in the `models.conf` format. `models.sh` reads them alongside `models.conf`.
- `adapters/local/`: extra adapter notes, for example a mapping from the generic terms in hughy-router ("a PR-tracking tool", "the closest available model") to one harness's tool names. hughy-router reads every file here after `adapters/pi.md`. A `blockers.env` here is sourced by `scripts/blockers.sh`, for example to set `HWORKS_HARNESS_AUDIT_LOG`. `scripts/kaizen-sessions.py` reads every `*.env` here, for example to set `HWORKS_TOOL_DIRS` to an overlay repo's tool dirs. `scripts/kaizen-tokens.py` reads them too, for example to set `HWORKS_OWNER_MAP` to name one harness's prompt sections and tools. `scripts/operator-signals.py` reads them too, for example to set `HWORKS_OPERATOR_SKIP` and `HWORKS_INJECTED_PREFIX` to one harness's injected text.

[`CUSTOMIZING.md`](./CUSTOMIZING.md#overlays) lists the terms an adapter maps and the layout of an overlay repo.

## Resync

```bash
git subtree pull --squash --prefix pstack https://github.com/hughy/pstack main
```

Then, for each row in `DIVERGENCE.md`, diff the mirror between the recorded commit and the new one for that skill and decide whether the reason still holds. `scripts/skill.sh list` shows what is linked.
